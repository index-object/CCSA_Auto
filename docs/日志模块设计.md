# 日志模块设计（2026-09 重构）

## 1. 为什么要重构

旧实现（`ccsa_auto/core/logger.py` 的原始版本）集中了四类问题：

| 问题 | 具体表现 |
| --- | --- |
| 多进程争抢同一文件 | NiceGUI 热重载的父子进程、重复启动的实例都往 `logs/app.log` 写；Windows 上文件被占用导致重命名失败，轮转静默失败，日志永远堆在一个文件里（“每天归档”失效） |
| 初始化有全局副作用 | 每个模块导入时都调用一次 `setup_logger()`，它内部执行 `logger.remove()` 再重新 `add`，重复创建 sink |
| 输出渠道不统一 | `loguru` 写文件、标准库 `logging.getLogger` 默认无 handler、大量 `print()` 走 stdout/stderr，内容分散且格式不一 |
| 内容不可用 | 任务执行、客户访问、错误提示混在一条流里，没有请求/任务上下文，无法按“一次任务”“一个客户请求”串联 |

## 2. 总体架构

重构后分为互相补充的两层：

```
                    ┌─────────────────────────────────────────┐
   运行期排障  ───►  │ 文件日志  ccsa_auto/core/logger.py       │
                    │  app / task / access / error 四渠道       │
                    │  每进程独立文件 + 每天归档 + 上下文注入    │
                    └─────────────────────────────────────────┘
                    ┌─────────────────────────────────────────┐
   后台可查询  ───►  │ 数据库台账  ccsa_auto/modules/logging/   │
                    │  app_logs（操作/认证/访问/系统/错误）     │
                    │  task_run_logs（精确到每次任务运行）      │
                    └─────────────────────────────────────────┘
```

* **文件日志**回答“当时到底发生了什么”，保留完整细节与调用栈；
* **数据库台账**回答“谁在什么时候做了什么”，可在管理后台筛选、分页、导出。

> 两者不是重复：文件日志是逐行的运行现场，台账是一次事件的摘要记录。

## 3. 文件布局

```
logs/
├── live/                                  # 运行期日志（每进程、每渠道一个文件）
│   ├── app.p<pid>_<启动时间戳>.log         # 系统/应用运行
│   ├── task.p<pid>_<启动时间戳>.log        # 任务执行
│   ├── access.p<pid>_<启动时间戳>.log      # 客户访问（JSON 行）
│   └── error.p<pid>_<启动时间戳>.log       # 所有 ERROR 及以上的汇总
├── archive/                               # 每日归档（按记录日期合并）
│   └── 2026-09-29/
│       ├── app.log
│       ├── task.log
│       ├── access.log
│       └── error.log
├── console/                               # 部署脚本重定向的 stdout/stderr
│   ├── app.out.log
│   └── app.err.log
└── .archive.lock                          # 归档用的跨进程文件锁
```

### 为什么“每进程一个文件”

两个进程**永远不会打开同一个日志文件**，因此：

* 不存在文件占用、重命名失败；
* 不存在两条记录交错写入；
* 进程崩溃时其日志文件自然封口，可安全归档。

进程标识取 `p<pid>_<启动unix时间戳>`，即使 PID 被操作系统复用也不会覆盖历史文件。

## 4. 日志格式与内容规范

### 4.1 文本渠道（app / task / error）

```
2026-09-29 07:13:01.482 | INFO  | task | trace_id=a1b2c3d4e5f6 task_id=1 task_name=每日一题 user_id=2 user_name=高默然 event=task_run | ccsa_auto.modules.task.scheduler:198 | [任务调度] 开始执行任务 | job_id=user_task_1 | task_type=daily | trigger=schedule | thread_id=5056 | execution_status=pending
```

字段顺序：`时间 | 级别 | 渠道 | 上下文键值对 | 模块:行号 | 消息`。

上下文键值对由 `contextvars` 自动注入，常见字段：

| 字段 | 含义 | 出现场景 |
| --- | --- | --- |
| `trace_id` | 一次任务执行的唯一链路 ID | 任务全流程 |
| `request_id` | 一次 HTTP 请求的唯一 ID（同时回写到响应头 `X-Request-ID`） | 客户访问 |
| `task_id` / `task_name` | 任务 ID / 名称 | 任务流程 |
| `user_id` / `user_name` | 用户 ID / 姓名 | 任务与访问 |
| `session_id` | 会话 ID | 客户访问 |
| `client_ip` | 客户端 IP（兼容 `X-Forwarded-For`） | 客户访问 |
| `path` / `method` / `status` | 请求路径/方法/状态码 | 客户访问 |
| `event` | 事件名，如 `task_run` / `page_view` | 各渠道 |

### 4.2 访问渠道（access）

每行是一个独立 JSON 对象，便于用 `jq` / pandas 统计：

```json
{"ts": "2026-09-29 07:13:01.482", "event": "page_view", "user_id": 2, "session_id": "…", "method": "GET", "path": "/admin_v2/logs", "status_code": 200, "duration_ms": 12.34, "client_ip": "10.0.0.5", "user_agent": "Mozilla/5.0 …", "referer": "https://…", "request_id": "a1b2c3d4e5f6"}
```

静态资源与 NiceGUI 内部通道（`/_nicegui`、`/socket.io`、`*.js` 等）不记录，避免刷屏。

### 4.3 错误渠道（error）

所有渠道中级别 `>= ERROR` 的记录会**额外**汇总一份到 `error.<pid>...log`，方便只看错误。建议业务代码在 `except` 中统一用 `logger.exception(...)` 以保留完整堆栈。

## 5. 数据库台账

### 5.1 `app_logs`（通用台账）

| log_type | 含义 | 写入位置 |
| --- | --- | --- |
| `operation` | 管理员操作 | `LoggingService.log_admin_operation` |
| `task` | 任务执行摘要（**失败日报依赖此类型**） | `LoggingService.log_task_execution` |
| `auth` | 登录/登出 | `LoggingService.log_auth` |
| `access` | 客户页面访问 | 访问中间件 → `LoggingService.log_access` |
| `system` | 应用启动/关闭、维护任务 | `LoggingService.log_system` |
| `error` | 错误 | `LoggingService.log_error` |

### 5.2 `task_run_logs`（精确任务运行记录）

**一次任务运行 = 一行**，由 `ccsa_auto/modules/task/scheduler.py::execute_user_task` 起止各写一次：

| 字段 | 说明 |
| --- | --- |
| `trace_id` | 与文件日志的 `trace_id` 对应，可互相检索 |
| `task_id` / `user_id` / `task_type` / `task_name` | 任务与用户标识 |
| `status` | `running` / `success` / `failed` / `skipped` |
| `trigger` | `schedule`（定时）/ `manual`（后台手动）/ `batch`（批量）/ `fixer`（修复器补跑） |
| `attempt` / `max_attempts` | 重试信息 |
| `started_at` / `finished_at` / `duration_ms` | 起止时间与耗时 |
| `total_questions` / `correct_questions` / `score` / `max_score` | 答题与得分 |
| `message` / `error_type` | 结果描述与错误分类（`AuthError` / `SubmitError` / `PlatformApiError` …） |
| `next_run_time` | 本次运行后计算出的下次运行时间 |
| `detail` | 原始结果 JSON（截断到 8000 字符） |

管理后台“操作日志 → 任务运行”标签页可按任务、用户、状态、类型、日期筛选，并展示最近 7 天成功率与平均耗时。

## 6. 如何在代码任意位置加日志

```python
from ccsa_auto.core.logger import get_logger, get_task_logger, log_context

logger = get_logger(__name__)            # 系统渠道
task_logger = get_task_logger(__name__)  # 任务渠道

# 1) 普通日志（自动带上当前上下文）
logger.info("用户 {} 更新了配置 {}", user_id, key)

# 2) 作用域内所有日志自动附加字段
with log_context(task_id=task.id, user_id=user.id, trace_id=new_trace_id()):
    task_logger.info("开始处理")
    ...
    task_logger.info("处理完成 | 耗时={}ms", cost)

# 3) 一次性附加字段
task_logger.bind(attempt=2, trigger="manual").warning("第 2 次重试")

# 4) 客户访问（写 access 渠道 JSON 行）
from ccsa_auto.core.logger import log_access
log_access(event="page_view", path="/x", method="GET", status_code=200,
           client_ip="1.2.3.4", user_id=1)
```

约定：

* 一个模块只在顶部获取一次 logger：`logger = get_logger(__name__)`；
* 不要再用 `print()`、`logging.getLogger()`、`from loguru import logger`；
* 日志消息保留中文，关键数值用 `{}` 占位符而不要拼进字符串，便于结构化检索；
* `except` 分支用 `logger.exception(...)` 保留堆栈；
* 需要串联一次完整流程时，先 `new_trace_id()`，再放进 `log_context`。

## 7. 每日归档

1. Loguru 在每天 `00:00` 轮转当前进程的 live 文件，并压缩为 `*.log.zip`（`rotation` / `compression` / `retention` 均由 `Config` 控制）。
2. 每天 `00:05`（`Config.LOG_ARCHIVE_HOUR/MINUTE`）以及**每次应用启动**，`archive_app_logs_job` 执行：
   * 先写一条心跳日志，促使 Loguru 完成跨天轮转；
   * 扫描 `logs/live`：处理 `*.log.zip` 轮转产物，以及**写它的进程已退出**的 `*.log`（绝不碰仍在写入的文件）；
   * 按**记录自身的时间戳**（而不是文件名）拆分成天，合并追加到 `logs/archive/<YYYY-MM-DD>/<渠道>.log`；
   * 删除已归档的源文件；
   * 清理超过 `LOG_RETENTION_DAYS` 天的归档目录（本轮刚写入的日期不清理）。
3. 归档使用 `logs/.archive.lock` 文件锁，保证同一时刻只有一个进程执行。

> 直接读当天日志时，用 `logs/live/` 下的文件；查历史用 `logs/archive/`。

## 8. 多进程 / 热重载注意事项

* **生产环境请保持热重载关闭**：`app.py` 使用 `reload=Config.APP_RELOAD`，默认 `False`（环境变量 `CCSA_RELOAD=1` 可临时开启）。热重载会派生子进程，导致父子进程重复初始化调度器与日志。
* `ensure_process_logging()` 会在请求入口、任务入口检测 PID 变化并自动重新绑定日志文件，因此 `fork`/`spawn` 出的子进程也不会写到父进程的文件里。
* `LOG_ENQUEUE` 默认 `False`（同步写、崩溃不丢日志、不存在跨进程共享队列问题）；确有需要可设为 `True`。
* 单个应用实例仍由 `deploy.ps1` 通过端口占用检测 + `Stop-Process` 保证。

## 9. 配置项（`ccsa_auto/core/config.py`）

| 配置 | 环境变量 | 默认 | 说明 |
| --- | --- | --- | --- |
| `LOG_DIR` | `CCSA_LOG_DIR` | `<项目根>/logs` | 日志根目录（默认绝对路径，避免随 cwd 漂移） |
| `LOG_LEVEL` | `CCSA_LOG_LEVEL` | `INFO` | 文件与控制台级别 |
| `LOG_RETENTION_DAYS` | — | `60` | 归档与台账保留天数 |
| `LOG_ROTATION` | — | `00:00` | 轮转时机 |
| `LOG_COMPRESSION` | — | `zip` | 轮转压缩格式 |
| `LOG_CONSOLE` | `CCSA_LOG_CONSOLE` | `1` | 是否输出控制台 |
| `LOG_ENQUEUE` | `CCSA_LOG_ENQUEUE` | `0` | 是否异步写 |
| `LOG_ACCESS_ENABLED` | `CCSA_LOG_ACCESS` | `1` | 是否记录访问文件日志 |
| `LOG_ACCESS_DB_ENABLED` | `CCSA_LOG_ACCESS_DB` | `1` | 页面访问是否入库 |
| `LOG_TASK_RUN_RETENTION_DAYS` | — | `90` | `task_run_logs` 保留天数 |
| `LOG_ARCHIVE_HOUR` / `LOG_ARCHIVE_MINUTE` | — | `0` / `5` | 每日归档时间 |
| `APP_RELOAD` | `CCSA_RELOAD` | `0` | NiceGUI 热重载 |

## 10. 运维与排障

* **看实时日志**：`logs/live/app.p*.log`、`task.p*.log`；
* **看某天的历史**：`logs/archive/2026-09-29/task.log`；
* **只看错误**：`logs/live/error.p*.log` 或对应归档；
* **按请求追踪**：用响应头 `X-Request-ID` 在 access/task 日志里 grep；
* **按任务追踪**：后台“任务运行”里的 `trace_id` 可回到文件日志；
* **日志状态自检**：`from ccsa_auto.core.logger import logging_status; logging_status()` 返回当前进程文件、归档天数、级别等；
* **手动归档**：`from ccsa_auto.core.logger import archive_logs; archive_logs()`。
